## 사용자 플로우

1. 홈 → [측정 시작] 탭 → (카메라 권한 프롬프트, `DEPLOY_ONLY`) → 측정 화면 LEARNING 시작.
2. LEARNING(~1.5s) 자동 완료 → ARMED, 상태 배너로 "타깃 대기 중" 표시.
3. 첫 차 통과 → ENROLLED, 타깃 색 칩 노출 + 플래시/햅틱. 색이 다르면 칩을 탭 → 재무장(ARMED로 복귀, 이전 미확정 데이터 폐기, 새 타깃 대기).
4. 이후 통과: 타깃 매칭 시 랩 확정(+피드백), 경계 매칭 시 랩+의심 배지, 타차 통과는 미세 틱만.
5. [정지] 탭 → `SESSION_DONE` → 결과 화면 자동 전환.
6. 결과 화면에서 랩 검토(의심 배지 수동 토글 가능) → 공유 또는 삭제(confirm) → 홈으로.

## 핵심 인터랙션

- **자동 타깃 등록**: 사용자 조작 없이 첫 통과로 확정. 유일한 수동 확인 지점은 색 칩 탭(재무장) — 제로 셋업 원칙(brief §1) 유지의 핵심.
- **색 칩 재무장**: 탭 1회 = `ARMED` 복귀 + 미확정 데이터 폐기. 즉시 실행, 취소 없음(ASSUMPTION, `gap-report.md` B6 — brief에 확인 UX 명시 없음).
- **통과 피드백 차등**: 타깃=플래시+햅틱(강한 신호), 타차=미세 틱(약한 신호) — 두 종류가 시각/촉각적으로 명확히 구분돼야 오인식을 막는다.
- **의심 배지**: 경계 매칭은 "랩으로 기록하되 의심 표시" — 추측으로 버리지도 조용히 넣지도 않는다(brief §2). 결과 화면에서 사용자가 사후 판단(토글).
- **상태 배너**: LEARNING/ARMED/재학습/60s 무통과/배경급변 등 예외를 배너로 정직하게 노출(brief §2 상태머신 예외 처리).

## UX Check

- **첫눈에 알 수 있어야 하는 것**: 측정 화면 진입 즉시 "지금 상태(학습중/대기중/타깃확보됨)"와 "현재 랩 진행 여부"가 한눈에 구분되어야 한다. 타깃 색 칩은 "지금 이 색을 쫓고 있다"는 사실을 명확히 전달해야 한다.
- **다음 행동이 보이는가**: 재무장이 필요한 순간(색 칩이 내 차가 아닐 때) 탭 대상이 명확한 affordance(칩 자체가 버튼처럼 보임)를 가져야 한다. 정지/토치 버튼은 상시 노출.
- **실수하거나 오해할 지점**:
  1. 의심 배지가 붙은 랩을 "틀린 기록"으로 오인해 무심코 삭제할 위험 — 의심≠오류라는 의미 구분이 필요하다.
  2. 타차 미세 틱과 타깃 통과 피드백이 시각적으로 유사하면 "내 차가 지나갔다"고 착각할 위험 — 강한 차등이 필요하다(brief R1과 직결).
  3. 재무장 탭 직후 이전 데이터가 조용히 폐기되는데, 되돌릴 수 없음을 사용자가 인지하지 못할 위험(brief R3).
- **먼저 정할 방향**: 재무장을 "즉시 실행"으로 할지 "짧은 취소 여지(예: 3초 undo 토스트)"를 둘지는 brief에 없다 — 제로 셋업 원칙상 즉시 실행을 기본(ASSUMPTION B6)으로 하되 Phase2 prototype에서 확인한다.
- **prototype/Phase 2에서 확인할 것**: 색 칩과 의심 배지의 정확한 시각 표현(색상 대비, 아이콘), 플래시/햅틱과 미세 틱의 체감 차이, 의심 배지의 문구/톤, "구분 어려움" 배너(R1 대응, 스티커 권장 안내)의 노출 시점.

## Design Direction

`_workspace/02_design/*`(design-system, layout-spec 등 시각 토큰)는 이번 ingestion 범위에서 생성하지 않는다 — 아래 항목은 그와 별개로 Phase2 디자인 착수를 위한 최소 방향이며, 미결 항목은 값을 지어내지 않고 `ASSUMPTION(프리뷰 A/B)`으로 표기한다.

- 브랜드 제약: 없음 — 브랜드 가이드/로고/지정 컬러 원문 없음(`gap-report.md` B3, 컴포넌트 라이브러리 미지정과 동일 근거).
- 참조 무드: 미지정. `ASSUMPTION(프리뷰 A/B)` — ① 야외 스포츠 계측기류(고대비·대형 숫자 중심) ② 미니멀 다크 대시보드류, 두 무드로 프리뷰 비교 후 확정.
- 밀도: `ASSUMPTION(프리뷰 A/B)` — 여백 중심(측정 화면은 핵심 수치 3개 내외만 대형 노출). 근거: `project-brief.md` §1(L17-19) 사용 시나리오상 폰을 레인 벽에 거치해두고 힐끗 확인하는 방식이라 고밀도 대시보드는 부적합.
- 다크모드: `ASSUMPTION(프리뷰 A/B, 근거 있는 기본값)` — 필수. 근거: 야외 트랙에서 폰을 멀리 두고 직사광선 아래 화면을 확인하는 사용 맥락(`project-brief.md` §1 사용 시나리오, §7 R6 저조도 리스크와 반대 극단인 눈부심 상황)상 고대비·저휘도 화면이 유리.
- 주 사용 기기: 모바일 세로 단일. 근거: `project-brief.md` §0 `WEB_PROFILE react-vite-spa` + §1 사용 시나리오(후면 카메라로 레인 바닥을 내려다보게 거치하는 폰 1대 사용, 데스크탑 사용 시나리오 없음).
- 용어·문구 톤: `ASSUMPTION(프리뷰 A/B)` — 기능적·간결체. 도메인 용어(랩/타깃/의심 배지/재무장 등)는 `project-brief.md`에 쓰인 표현을 그대로 채택하고, 정확한 안내 문구(권한 거부, 저사양 강등 등)는 Phase2에서 확정(`gap-report.md` I3, I5).

단, 색 칩의 "정확한 타깃 색 표시"는 시각 디자인이 아니라 기능 요구(FR-C2, 데이터 정확성)이므로 이 구분을 유지한다.
